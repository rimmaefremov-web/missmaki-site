## Проверка существующей корзины

Настоящий Supabase JS и HTML тестового магазина выполнили оформление вымышленного предзаказа **№2**: сумма 470 ₽, статус new. Заказ прочитан обратно через API, адаптивность проверена на ширине 390 px.

Ограничение испытания: браузер запускается в изолированном окружении, где прямой запрос к API завершался Failed to fetch. Для этой проверки HTTP-запросы браузерного SDK направлялись в тот же реальный API через Python HTTPS-клиент с обычной проверкой TLS и настроенным прокси. База и RPC были настоящими; это проверка протокола SDK и корзины, **не доказательство прямой работы HTTPS/CORS на iPhone или WebSocket/Realtime**. Проверку с физического устройства на публичном тестовом домене ещё нужно выполнить.

Из-за выключенного anonymous режима для частичного испытания использовались зарегистрированные **вымышленные** покупатели с адресами @example.invalid и случайными паролями. В обычный код магазина такой способ регистрации не добавлен. Ни настоящая почта клиента, ни настоящий телефон не использовались; SMS/звонки не выполнялись. Созданы две вымышленные учётные записи Auth, без роли staff.

Оба заказа, №1 и №2, помечены **«АВТОТЕСТ — НЕ ГОТОВИТЬ»**. Они остаются в тестовой базе со статусом new. Публичного ключа недостаточно для их отклонения — это проверенное ограничение прав, а не повод его обходить. После входа сотрудника их можно отклонить в кухне. Существующие заказы и их статусы не изменялись.

## Что не проверено

- Вход **существующего администратора** и его роль: пароль и авторизованная сессия владельца не передавались. Вход обычного вымышленного покупателя этого не доказывает.
- Положительное выполнение всех времён администратором в настоящем проекте. Локальные SQL/браузерные тесты этих кнопок имеются; реальный прогон требует входа владельца.
- Гостевое оформление через signInAnonymously — сейчас невозможно, получен явный отказ провайдера.
- Публичная тестовая ссылка, физические iPhone/iPad, звук, Realtime, бэкапы и восстановление.

## Что выяснено об Anonymous Sign-ins

[Документация Татнет Studio](https://docs.tatnet.ru/docs/platform/supabase-studio) описывает Email, URL Configuration, Rate Limits, но не подтверждает переключатель anonymous-входа. На конкретном проекте GET /auth/v1/settings вернул external.anonymous_users=false, а POST /auth/v1/signup без email/пароля — HTTP 422 с кодом anonymous_provider_disabled. Это доказывает выключенный режим в этой базе, но **не доказывает**, что Татнет способен включить его через поддержку.

[Обычный Supabase поддерживает anonymous-вход](https://supabase.com/docs/guides/auth/auth-anonymous). Для самостоятельно установленного Auth настройки могут управляться серверной конфигурацией, а не Studio ([документация](https://supabase.com/docs/guides/self-hosting/auth/config)). Настройку управляемого Татнет должен подтвердить его оператор. Переключать базу на Pro ради этого без подтверждения не следует: в найденных документах связь с тарифом не указана.

Предпочтительное решение: поддержка включает штатный anonymous-вход **только в MissMaki-test**, затем повторяем реальный гостевой сценарий. Секретные ключи для этого исполнителю не нужны.

Если режим нельзя включить, сохраняются два технических пути: отдельный сервер выдачи индивидуальных гостевых сессий в РФ (новая серверная часть, отдельные секреты и защита от спама на сервере), либо перенос тех же SQL/RLS/RPC и клиентского кода в собственный Supabase на российском VPS, где конфигурация Auth контролируется. Для минимальных изменений в коде предпочтителен второй путь, если провайдер окончательно подтвердит отсутствие нужного режима. Ничего не покупалось и не переносилось. Общая гостевая учётная запись для всех покупателей не подходит: она разрушит изоляцию заказов.

## Как продолжить тесты без anonymous-входа

В /kitchen/diagnostics.html появился флажок **«Если гостевой вход выключен: использовать две вымышленные тестовые учётные записи»**. После локального входа владельца диагностика создаёт их только для испытания, проверяет все 8 времён, отказ, изоляцию, стоимость и историю на новом вымышленном заказе. В отчёте явно указывается customerAuthMode=synthetic-email и guestCheckoutVerified=false; это не успешная проверка гостевого магазина. Почтовая регистрация должна уже работать и выдавать тестовую сессию; отключать подтверждение почты специально для прогона не нужно.

Публичная HTTPS-ссылка тестовой версии пока не создана: доступа к отдельному тестовому хостингу в задаче нет. Подготовлен архив с уже вставленными **публичными** настройками. В него не включены тестовые пароли, JWT или токены сессий. Исполнитель не сможет проверить роль владельца, пока владелец не войдёт в тестовую кухню локально.
