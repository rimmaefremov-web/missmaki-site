# Завершение MissMaki Кухня без новой базы — 2 ноября 2026

Работаем с существующими MissMaki-test, `https://missmaki-site.tatnet.app/` и веткой `codex/missmaki-kitchen`. Один покупательский механизм — Supabase Anonymous Auth. Новые проекты/базы, платные ресурсы и аккаунты не создаются. 003 не применять. Рабочий missmaki.ru и main не переключены; PR остаётся draft.

## Исправление повторной модерации

Подготовлен `supabase/migrations/004_review_moderation_idempotency.sql`: после 001/002, независимо от 003. Исполняется одной транзакцией, повторное применение допустимо. Меняет только функцию moderate_review и её права EXECUTE; не трогает пользователей/UID/admin, таблицы, отзывы, RLS, Auth или цены. Нет удаления старых дублей истории: это сохранённый след ранее выполненных действий.

Сервер сначала проверяет staff и допустимый статус, блокирует строку отзыва. Если состояние уже такое же — успешный возврат без UPDATE, роста версии или события audit, даже при повторе старого запроса. Для реального противоположного решения нужна актуальная версия; NULL-версия больше не обходит защиту. Повторный запрос от покупателя остаётся запрещённым даже при совпадающем статусе.

В интерфейсе кнопка текущего решения отключается. Другая остаётся доступной; смена уже принятого решения требует подтверждения. При pending подтверждение первого решения не добавляется. Отклонённый отзыв не попадает в public_reviews; автор по-прежнему получает pending, текст «Ваш отзыв ожидает подтверждения». Принятие публикует, последующее отклонение скрывает его снова.

**На настоящей базе 004 агентом не применена:** публичный ключ не даёт права менять SQL-функции. Старую серверную ошибку нельзя считать устранённой до применения файла, даже если интерфейс уже обновлён. Для серверной проверки нужен вход staff в браузере владельца; пароль в чат не передаётся.

### Действия на iPhone — один SQL-файл

1. Открыть [004_review_moderation_idempotency.sql](https://github.com/rimmaefremov-web/missmaki-site/blob/codex/missmaki-kitchen/supabase/migrations/004_review_moderation_idempotency.sql), нажать Raw и скопировать весь текст.
2. Татнет → **существующая MissMaki-test → Studio → SQL Editor → New query**, вставить → **Run**. 001/002 повторять не надо; 003 не нужна. Ничего в файле менять не требуется.
3. После Success обновить `/kitchen/`. На тестовом отзыве нажать «Отклонить»: эта кнопка станет недоступна. Проверить историю — одно новое событие; лишних «Отклонён → Отклонён» не должно появляться.
4. «Принять» → подтвердить: отзыв появляется на тестовом магазине. «Отклонить» → подтвердить: отзыв исчезает у другого посетителя, у автора остаётся сообщение ожидания после reload. Проверить два устройства/две вкладки сотрудника: устаревшее противоположное решение должно потребовать обновления.
5. Не удалять прежние дубли истории вручную. При ошибке SQL передать текст ошибки без секретов, не отключать RLS.

## Результаты проверки

- `npm test`: **35 / 35**; `npm run build:preview`: успешно. В PostgreSQL/PGlite проверены повтор одинакового статуса с прежней и текущей версией, отсутствие роста audit/version, смена решения, запрет покупателю, NULL/устаревшая версия, повторное применение 004. Публичная выдача и внешний pending проверены после обеих смен решения.
- Браузер: 27 сценариев на размерах телефона/планшета/desktop. Проверены выключенная кнопка текущего решения, отмена/подтверждение противоположного; настоящий Web Audio API запускает генератор после жеста, один сигнал при новом заказе без повторного сигнала на одинаковое обновление, приостановка и повторное включение. Это техническая проверка вызовов аудио, **не доказательство слышимого звука на iPhone**.
- Соединение: предупреждение offline, автоматическая сверка на online, возврат к экрану, обновление статуса; восстановление не создаёт новый заказ. Применяются Realtime и резервная сверка каждые 3 секунды. Сбой звукового API теперь не мешает обновлению списка заказов.
- Настоящий API: Auth anonymous включён, публичная выдача сейчас пустая (HTTP 200). По пустому списку нельзя доказать правильность обработки конкретного отклонённого отзыва без его ID/служебного доступа; это не подмена проверки модерации.
- Два ограниченных запроса anonymous signup без CAPTCHA дали 200, разные сессии; logout обеих — 204. Новые заказы/отзывы в этой проверке не создавались. JWT/refresh-токены не сохранялись. Анонимные пользователи остаются в Auth как след теста.

## Защита от массовых анонимных входов: пока не подтверждена

Два успешных входа без CAPTCHA показывают, что сервер не требует решения CAPTCHA на этом пути. Они **не доказывают отсутствие лимита на 30-й/100-й запрос**. Массовое создание пользователей ради проверки не выполнялось, чтобы не расходовать Free и не блокировать покупателей/владельца.

В SQL 001 лимит 5 заказов за 10 минут на UID и 3 отзыва в час на UID, серверная цена и запрет прямой записи. Новый UID получает новый бюджет; это не общая антиспам-защита. Ограничение в JavaScript не закрывает прямой `/auth/v1/signup`. Исходный Supabase описывает стандартный лимит anonymous 30/IP/час и рекомендует CAPTCHA, но переносить эту цифру на управляемую установку Татнет без проверки нельзя: https://supabase.com/docs/guides/auth/auth-anonymous .

**Необходимый результат перед рабочим запуском:** подтвердить у Татнет действующие лимиты anonymous signup по достоверному IP, доверие заголовкам только от собственного прокси, отсутствие обхода через публичную email-регистрацию, общий предел создания пользователей/заказов и подходящий российский антибот либо поддерживаемый Auth hook. Изменение параметров Auth/прокси выполняется только с согласованием владельца. CAPTCHA только на форме без обязательной серверной проверки не подходит. Не подключать Cloudflare/Google/hCaptcha автоматически.

Владелец может открыть **MissMaki-test → Authentication → Settings → Rate Limits**, сообщить только названия и числовые значения полей, без секретов. Если поля anonymous отсутствуют — следующий текст для обращения поддержке (агент его никуда не отправлял):

> Для существующей MissMaki-test (Free) включён anonymous Auth. Подтвердите действующие лимиты `/auth/v1/signup` для anonymous по реальному IP и по проекту, серверную защиту от обхода через email signup, защиту от подмены IP-заголовков и доступный на Free российский антибот/Before User Created hook. Просим согласовать безопасный ограниченный тест 429 без создания множества пользователей. Нужно сохранить staff-вход и текущие UID, без новой базы и изменения тарифа. Также нужны условия резервного копирования/восстановления и доступности Free.

До ответа/проверки этого пункта рабочие заказы подключать преждевременно. Кодом браузера подтвердить скрытые настройки Auth невозможно.

## Татнет Free для постоянной работы

Проверены официальные страницы 2 ноября 2026: [Supabase](https://docs.tatnet.ru/docs/platform/supabase), [Studio](https://docs.tatnet.ru/docs/platform/supabase-studio), [тарифы](https://tatnet.ru/pricing).

База Free: до 100 МБ (старые до 11 сентября могут иметь 500 МБ — смотреть карточку), 5 ГБ трафика/месяц, 200 Realtime-подключений, 100 API-запросов/с, пауза после 7 дней без обращений. При превышении места/трафика провайдер описывает остановку записи и входа пользователей; после паузы API 503 до ручного возобновления. Pro не включался. Пауза Studio сама по себе не равна паузе базы.

**Вывод:** Free подходит для нынешних испытаний; достаточность для непрерывного приёма реальных заказов пока не подтверждена. Нужно измерить реальные расход/объём и иметь проверенное восстановление. По найденным публичным страницам не подтверждены SLA и гарантированное автоматическое резервирование Free. Это отсутствие подтверждения, а не утверждение, что резервных копий нет.

Резервная сверка каждые 3 секунды может расходовать трафик даже при отсутствии новых заказов: для примера, 100 КБ ответа каждые 3 с круглосуточно — около 2,88 ГБ/сутки (условный расчёт, не измерение вашей базы). После накопления истории понадобятся меньшие выборки/дельты и адаптивная сверка; ускорять обращения для искусственного обхода паузы не планируем. Фото уже находятся на статическом сайте и не загружаются заново в БД.

## Очерёдность окончательного запуска

1. **Сейчас:** применить только 004 в MissMaki-test и выполнить сценарий модерации выше. Сборка обновляется из текущей ветки; при необходимости перезагрузить тестовую страницу. Одна существующая база, без новой настройки пользователя.
2. **Далее на тестовом адресе:** повторить все восемь времён/отказ, принятие/отклонение отзыва, отмену смены решения и восстановление после потери ответа. Два устройства: покупатель и сотрудник; только вымышленные данные.
3. **Физические iPhone/iPad:** нажать «Включить звук», убедиться, что сигнал слышен при новом заказе; выключить Wi-Fi/мобильную сеть, вернуть её, сверить отсутствие потерь/дублей. Свернуть/развернуть Safari и PWA, проверить предупреждение, снова включить звук при необходимости. В фоне/при блокировке гарантий без push нет.
4. **До рабочего допуска:** завершить согласованный тест антиспама и 429; получить подтверждения поддержки о Free, резервировании/восстановлении и локализации первичной записи/журналов/копий в РФ. Подготовить безопасную копию текущей БД и испытать процедуру восстановления без удаления/пересоздания текущей базы. Не отправлять дампы с данными в чат.
5. **Измерения на той же базе:** несколько дней обычной вымышленной работы и сверка расхода в карточке; затем контроль минимум за 7 дней. Определить порог предупреждения задолго до 100 МБ/5 ГБ, доступ владельца к кнопке возобновления и порядок действий при read-only/503. При недостаточности Free решение согласовать отдельно; ничего платного автоматически не включать.
6. **Подготовить один конкретный релиз:** сохранить текущую версию сайта, меню/фото/корзину; проверить каталог/цены, документы/согласия/сроки хранения, разграничение staff и контрольный заказ. Существующую MissMaki-test не переносить: можно использовать эту же базу после осознанного допуска, сохранив пользователей, SQL и UID. Тестовые записи не удалять автоматически; заранее пометить и исключить из реальной работы по согласованному списку.
7. **Только после отдельного согласия владельца:** объединить проверенный PR/опубликовать подготовленную рабочую конфигурацию и включить один новый транспорт с отключением старых Telegram/GAS в том же релизе, не создавая двойной отправки. Контрольный заказ из рабочего магазина → staff → время → покупатель. При сбое закрыть отправку с честным сообщением; не включать старую и новую отправку одновременно. Иметь контактный номер для заказов на время сбоя.

Пока шаги 1–5 не приняты, обещать готовность к постоянной работе нельзя. Рабочий домен не изменяется без отдельного согласия.
