# Настоящая MissMaki-test после INSTALL_FINAL — 2 ноября 2026

Владелец выполнил INSTALL_FINAL.sql. Агент подтвердил реальный GoTrue/REST на существующей базе: **29 проверок API прошли**. SQL повторно не применялся, тариф/домен/PR не менялись.

Подтверждено: anonymous включён; прямой signup без доказательства и поддельное/повторное доказательство отклоняются; подписанный challenge и корректный proof создают независимые анонимные сессии; metadata сверх 8 КБ не сохраняются; обновление сессии работает. GoTrue возвращает использованный публичный proof в первоначальном ответе своей модели, но повторный GET /auth/v1/user подтверждает, что в сохранённом профиле его нет. Это не серверный секрет; повтор signup с ним отклонён. Отрицательные signup-проверки получают штатную для этой установки HTTP 500, а корректный вход — 200.

Создан один вымышленный предзаказ **№7 «АВТОТЕСТ ФИНАЛ — НЕ ГОТОВИТЬ»**. Две одновременные отправки дали одну запись; заказ читается владельцем и после обновления сессии, чужим покупателем/без сессии недоступен. Подмена цены/тела повтора, прямое изменение статуса, принятие покупателем и скрытие им заказа как тестового запрещены.

business_backup запрещён покупателю и без сессии. Положительный экспорт admin **не проверен агентом**: сессия владельца находится на его устройстве, и её нельзя получить из публичного ключа. Функция существует, и проверка ролей срабатывает; это не доказательство, что пользователь сохранил резервный файл.

Через настоящий опубликованный сайт и SDK/Worker пройдены **11 браузерных проверок**: анонимный вход, выбранный режим Auth, цена корзины 470 ₽, загрузка фотографий, отсутствие старых Google/Telegram-запросов, сохранение request_id/имени/корзины после reload, корректная ошибка без ложного принятия при имитации HTTP 503. Запрос create_order перехвачен до сервера, нового заказа этот браузерный сценарий не создавал. Для CA прокси среды в Chromium использован ignoreHTTPSErrors; это не проверка сертификата физического iPhone. Физическую работу кухни владелец подтвердил ранее.

Тестовые сессии завершены HTTP 204; JWT/пароли/refresh-токены в отчёты не записывались. Анонимные технические пользователи остаются в Auth, не удалялись. Нагрузкой не исчерпывались реальные 60/час, 300/сутки или бюджеты заказов: их алгоритмы/границы проверены PostgreSQL/PGlite, исчерпание на настоящей базе остановило бы обычных покупателей. Не обещается DDoS-защита.

## Последний необходимый шаг владельца

В кухне **«Резервная копия» → «Создать зашифрованную копию»**, задав и повторив пароль файла, сохранить в «Файлы → На моём iPhone/iPad». Этот экспорт обратимо пометит только точно известный №7 как тестовый по совпадению UUID+request_id+имени и уберёт его из очереди, не удаляя данные; после отметки снимок запрашивается заново. Никакие похожие имена или реальные записи не трогаются. Администратор может снять отметку в истории.

После успешного экспорта интерфейс показывает количество записей. Пока владелец не подтвердил сохранение, агент не заявляет, что реальная резервная копия создана. Это ручная копия заказов/отзывов/аудита, а не полный снимок Auth или автоматическое фоновое сохранение. Восстановление проверено локально исполняемым SQL; реальную базу ради проверки не стирали/не откатывали.
