# Развёртывание для исполнителя

**Новый подготовленный вариант:** гостевой токен + серверная проверка PostgreSQL, без регистрации в Auth и без Pro. См. [ГОСТЕВЫЕ-ЗАКАЗЫ-FREE.md](ГОСТЕВЫЕ-ЗАКАЗЫ-FREE.md). 003 не применена к Татнет. Старые инструкции ниже описывают исходный Auth-вариант; после 003 используйте сборку `--database-guests` или `npm run build:preview`. Не запускайте прежнюю email-диагностику: её обходной путь намеренно закрывается миграцией.

## Архитектура и границы

Текущий рабочий GitHub Pages не переключается. Для будущей эксплуатации выбран кандидат — российский управляемый Supabase Татнет; подробности и условия допуска: [РОССИЙСКОЕ-РАЗМЕЩЕНИЕ.md](РОССИЙСКОЕ-РАЗМЕЩЕНИЕ.md). Код сайта сохраняется; последующий перенос тех же файлов в РФ — отдельное действие после испытаний. `shared/config.js` по умолчанию выключен и содержит пустые публичные настройки. При enabled=false исходный путь заказов сохранён. При enabled=true `shared/customer.js` заменяет отправку, проверку предзаказов, наблюдение за заказом и отзывы. В новом пути нет запросов в Telegram или Apps Script. Не включать флаг на рабочем сайте до приёмки.

Supabase Auth: покупатель — anonymous authenticated session, сотрудник — email/password и запись в `staff`. Сессии магазина и кухни имеют разные storageKey. Роль назначается только владельцем через SQL Editor; браузер не может менять staff. Все записи — security-definer RPC с фиксированным search_path и явными правами EXECUTE. RLS разрешает читать только свой заказ или сотруднику. Публичный RPC отзывов возвращает только approved и только публичные поля. Даже автору отклонённого отзыва my_reviews возвращает pending. Таблица reviews не даёт автору читать отклонённый внутренний статус. Audit недоступен покупателю.

Время, цены, подарок, доставка, часы работы и слот предзаказа проверяются сервером. Каталог извлечён из существующих groups и ORDER_SKUS, цены в рублях. Изменения меню должны включать обновление серверного каталога, иначе сервер отклонит устаревшую стоимость. Слот предзаказа резервируется уникальным индексом (один новый/принятый заказ на слот, как в текущей проверке занятости); реальную ёмкость кухни согласовать до запуска.

Realtime Postgres Changes ускоряет обновления; независимая сверка каждые 3 секунды восстанавливает состояние после разрывов и ловит скрытую от автора модерацию. SLA «мгновенно» зависит от соединения. Отсутствие Realtime не теряет заказ; служебный индикатор отражает успешность последних запросов к БД. HTTP-запросы ограничены 15 секундами; отсутствие успешной сверки дольше 15 секунд включает предупреждение. При восстановлении загрузка идёт из БД. Не обнулять историю в клиентском коде. Аудио требует жеста пользователя; push не реализован. Service worker кэширует только оболочку кухни, не API и не ключи/сессии.

## Подготовка

1. Выполнить оба SQL-файла в порядке номеров в отдельном тестовом проекте Supabase. Миграция 001 рассчитана на однократное выполнение.
2. Включить anonymous sign-ins, создать сотрудников через Admin UI и выдать роль через staff. Доступ сотрудника определяется staff, а не фактом email-регистрации. Не отключать общий Allow new users to sign up: он может отключить и anonymous-вход. Отдельные настройки email-регистрации должны сохранять вход уже созданных сотрудников. На текущей MissMaki-test anonymous-вход реально отклоняется; см. ПРОВЕРКА-TATNET-2026-11-01.md. Не ослаблять RLS ради тестов.
3. Убедиться, что orders/reviews входят в publication supabase_realtime (миграция добавляет их). Для authenticated не добавлять широких write-политик и не выдавать service_role браузеру.
4. На staging-копии выставить настоящие Project URL и publishable/anon key, enabled=true в shared/config.js. Эти значения публичны. Никаких вымышленных рабочих реквизитов. В Supabase Auth установить Site URL и разрешённые redirect URL тестового и основного домена.
5. Библиотека Supabase 2.110.0 хранится в shared/vendor/ с лицензией и SHA-256; браузер не обращается к jsDelivr. Проверить HTTPS/WSS к реальному российскому API, права и лимиты, фактическое размещение Auth/БД/бэкапов/логов. У Татнет сначала подтвердить поддержку anonymous sign-ins; публичные документы Email/Auth не доказывают её наличие.
6. Настроить серверные лимиты по IP для анонимных регистраций/записей и защиту входа сотрудников на российском API. Ограничение RPC на UID не защищает от смены UID. В профиле ru запрещены Supabase Cloud (*.supabase.co) и Cloudflare CAPTCHA; не включать Turnstile. Если российский провайдер не предоставляет нужной защиты, публичный приём заказов не запускать до её реализации. Не утверждать, что лимит API в запросах/секунду заменяет защиту от спама.
7. Настроить производственный тариф без паузы, мониторинг ошибок, резервное копирование и проверку восстановления. Политику удаления/обезличивания ПД и резервных копий определяет владелец; автоматический retention job здесь не включён. Audit хранит UID сотрудника и события; журнал неизменяем через API.
8. Подтвердить поручение обработки, реальное российское размещение и административный доступ; утвердить документы и сроки хранения с владельцем. До подтверждения восстановления полной БД и Auth, выгрузки, SLA и защиты API выбранный сервис — только кандидат. Если требования не выполняются, резервный вариант — self-hosted Supabase на российском VPS. Инфраструктура этим PR не развёрнута.

## Проверка и переключение

```sh
npm ci --cache /tmp/mm-npm
npm test
PLAYWRIGHT_BROWSERS_PATH=/tmp/mm-browsers npx playwright install chromium
PLAYWRIGHT_BROWSERS_PATH=/tmp/mm-browsers npm run test:browser
```

Автоматические браузерные тесты используют fake API; запускать реальную приёмку по ПРИЁМКА.md отдельно. Не подменять её результатами mock-тестов.

Для уже созданной владельцем MissMaki-test доступна сборка с вводом настроек через браузер: `node scripts/build-russian-preview.mjs --setup --output /tmp/missmaki-test-preview`. Пошагово: [ПОДКЛЮЧЕНИЕ-ТЕСТОВОЙ-БАЗЫ.md](ПОДКЛЮЧЕНИЕ-ТЕСТОВОЙ-БАЗЫ.md). Диагностика входит только в экспорт; source config.js остаётся выключенным.

Подготовить **отдельный тестовый экспорт** (только настоящий URL и публичный ключ из пустого тестового проекта):

```sh
node scripts/build-russian-preview.mjs 'НАСТОЯЩИЙ_HTTPS_API_URL' 'ПУБЛИЧНЫЙ_ANON_KEY' --output /tmp/missmaki-preview
```

Это команда для исполнителя, не для владельца с iPhone. Она не делает сетевых запросов, не создаёт базу, не публикует сайт и не меняет DNS. Выходная папка должна быть новой и вне репозитория. В неё попадают только HTML, assets, kitchen и shared; .git, секреты, CNAME, тесты и инструменты не копируются. Старый транспорт удаляется в экспорте, конфигурация включает только тестовую копию с предупреждением «Только вымышленные данные». Не переносить в неё реальные заказы. Флаг ru — защита от очевидной ошибочной настройки, не геолокация и не сертификат соответствия.

Для тестовой публикации подготовить этот экспорт на отдельном российском preview-домене. Не подключать missmaki.ru и не использовать автоматический production-деплой текущей ветки. Если Apps определяет корневой package.json как Node-приложение, публиковать именно статический экспорт без package.json; это существующий HTML-сайт, сборка приложения не нужна. Account, SQL Editor и служебный доступ пока отсутствуют.

После реальной приёмки отдельным изменением можно подготовить финальный diff:

```sh
node scripts/enable-kitchen.mjs 'НАСТОЯЩИЙ_HTTPS_API_URL' 'ПУБЛИЧНЫЙ_ANON_KEY' --verified
```

Не запускать эту команду для текущего рабочего сайта в рамках проверки вариантов размещения. Скрипт поддерживает HTTPS API российского managed/self-hosted Supabase, проверяет формат публичного ключа, отклоняет Supabase Cloud. Ключи JWT проверяются только по виду и роли anon, а не криптографически: действительность и принадлежность проекту проверяются на реальном API. Скрипт удаляет старый транспорт и JSONP, закрывает старую тестовую копию редиректом и подготавливает юридические тексты. Перед production владелец/исполнитель обязаны внести в политику действительные сведения о провайдере и площадке: скрипт их не угадывает.

Для staff: создать тестового пользователя в Studio → Authentication → Users, затем выполнить в SQL Editor:

```sql
insert into public.staff(user_id,role)
select id,'admin' from auth.users where email='ПОЧТА_ТЕСТОВОГО_АДМИНИСТРАТОРА';
```

Для отключения удалить запись staff; доступ к SQL/Studio не выдавать обычным сотрудникам. Оператор БД с правами владельца обходит RLS — держать этот доступ отдельно от кухни. Настроить Site URL тестового домена и разрешённые redirect URLs без широкого `*`.

Повторить тесты на полученной версии, проверить, что сетевых обращений к script.google.com/Telegram нет. Production-размещение и DNS разрешаются только после реальной приёмки и отдельного решения владельца; текущий PR оставить draft и не объединять. Рассмотреть публикацию тех же файлов в РФ, оставив исходники в GitHub без данных покупателей. Сохранить старые записи для истории. После переключения принять уже отправленные в старую систему заказы, отключить старый Apps Script deployment/триггеры и Telegram-обработчик у их владельца, отозвать старые токены. Доступа к этим внешним настройкам в задаче нет. Не делать двойную отправку или «резервное» автоматическое отправление в Telegram. Старые открытые вкладки магазина следует обновить; для перехода выделить короткое окно без новых заказов.

Сначала новая система выключена. Это ещё не отключение старой системы на production. После вырезания старого транспорта новый путь не делает fallback даже при сетевой ошибке.

## Операционные особенности

- История и отзывы загружаются порциями по 100, кнопка «Показать ещё». Новые заказы догружаются все порциями по 500. При настройке PostgREST оставьте max_rows не менее 500. История и отзывы используют range-пагинацию, чтобы не упираться в стандартное ограничение ответа 1000 строк.
- Одинаковый request_id в рамках UID возвращает прежний заказ; изменённое тело с прежним ID запрещено. SHA-256 fingerprint и Web Locks помогают повторной отправке между вкладками; без Web Locks сервер также объединяет одинаковое тело заказа одного покупателя в течение 10 минут под блокировкой, возвращая канонический requestId. Повторить намеренно полностью одинаковый заказ в этот интервал отдельной записью нельзя. Два разных устройства/браузера имеют разные сессии и намеренные заказы — не считаются дублем.
- При потере ответа сохраняются request_id и черновик до подтверждения, можно восстановить форму и повторить с тем же ID. После ответа черновик удаляется. Очистка браузера удалит возможность клиентского восстановления; сотрудник всё равно видит сохранённый заказ.
- Не сообщать покупателю об отклонении отзыва. На публичном сайте и в my_reviews отказ выглядит как ожидание. Фотографии отзывов не принимаются: прежде форма была заглушкой, в новой системе доступны требуемые имя/оценка/текст. Storage загрузок не развёрнут.
- Менять статусы и модерировать могут обе роли staff; только владелец Dashboard управляет составом сотрудников. Конкурентная правка отсекается version и блокировкой строки.
- PWA офлайн показывает оболочку с предупреждением. Офлайн-подтверждений заказов нет; операции не ставятся в скрытую очередь.
