# Подготовка запуска MissMaki.ru — итог на 2 ноября 2026

**Рабочий сайт не переключён, PR не объединён.** Действуют прежние репозиторий, ветка и MissMaki-test Free. Владелец подтвердил физическим испытанием на планшете: вход, новые заказы, слышимый звонок/повтор 30 секунд, принятие/отказ и модерация работают. Не требуется повторять настройку с нуля.

## Готовый пакет вместо немедленного переключения

`node scripts/prepare-launch.mjs --config PUBLIC_CONFIG_JSON --output NEW_DIRECTORY_OUTSIDE_REPO` собирает всё локально, без HTTP/SQL/публикации. JSON содержит только существующие публичные `{ "url": Project_URL, "key": publishable_key }`; пароли и service_role запрещены валидатором.

- `candidate/`: версия для будущего запуска, production-конфигурация с той же базой и одним Anonymous Auth, без тестового баннера, /setup и диагностических страниц. Старый транспорт Telegram/GAS удаляется только в копии.
- `safe-fallback/`: тот же дизайн/меню/фото/корзина, новые отправки заказов/отзывов из интерфейса остановлены с понятным сообщением. Уже сохранённые заказы продолжают получать статусы, кухня продолжает их обработку. Это откат клиентского интерфейса, не базы.
- `site-before.zip`: точный архив origin/main с зафиксированным SHA. **Для сохранности, не публиковать автоматически:** там прежние интеграции, их работоспособность не подтверждена. Их повторное включение может создать дубли.
- `release-manifest.json`: SHA исходной и подготовленной версии, хеши файлов/меню/фото, явные блокеры; `notDeployed=true`. Не считается разрешением на запуск.

Дополнительно read-only GET настоящего missmaki.ru (HTTP 200) подтвердил совпадение массива меню/цен и встроенных фотографий с текущим исходником и origin/main. Рабочий файл не изменялся.

Меню/цены и встроенные фото сравниваются с исходником автоматически. Файлы блюд копируются без изменения. Корзина и оформление сохраняются. В уже подготовленном пути загрузка фотографий **к отзывам** не реализована и скрыта: это отдельно от фотографий блюд, которые сохранены. Не выдаём её за работающую функцию. При необходимости загрузки отзывов запуск этого расширения требует отдельного решения.

## 1. Антиспам — подготовлен дополнительный серверный слой, но Auth ещё не допущен

`supabase/migrations/005_submission_budgets.sql` подготовлен, **не применён автоматически**. Начальные тестовые общие бюджеты: заказы 10/мин и 200/сутки, отзывы 5/мин и 100/сутки на всю базу. Это фиксированные окна, не скользящие. Требуется согласовать значения с реальным потоком; они могут отказать обычным покупателям в пик или после атаки.

Защита выполняется триггерами БД, действует при смене UID и через email-аккаунты, не зависит от JS. Счётчики меняются атомарно; существующие повторы возвращают прежний заказ до INSERT и не расходуют бюджет. Таблицы лимитов закрыты для клиентов. Учитываются только успешно сохранённые строки: откат транзакции откатывает бюджет. Цены/валидация/история/права существующих функций сохранены. Остаётся 4 счётчика, их число не растёт со временем. Миграция повторяема, не удаляет данные/пользователей, независима от 003/004; 003 не нужна.

Это ограничивает рост **заказов/отзывов**, но не создание записей `auth.users`, не сетевой DDoS и не все неуспешные попытки. Публичный `/auth/v1/signup` требует подтверждённых провайдером ограничений и антибот-защиты с обязательной серверной проверкой. До этого нельзя утверждать, что массовые анонимные регистрации защищены. Ранее два ограниченных signup без CAPTCHA проходили; эти проверки не доказывают отсутствие более высокого порога. Массовый тест, изменение Auth и установка зарубежной CAPTCHA не выполнялись.

На Free предусмотрен глобальный предел API по документации, но он не заменяет антиспам пользователей: большая частота ниже этого предела всё равно может заполнить Auth/базу. Нельзя решать проблему только выключением формы или скрытием публичного ключа.

## 2. Потеря связи и честные сообщения

Ранее проверены идемпотентный request_id, сохранение черновика до подтверждения записи, восстановление корзины/заказа после reload и повтора потерянного ответа. Клиент не может сам установить accepted. Время появляется только после чтения реального статуса кухни.

Добавлена проверка ответа create_order до удаления черновика: требуется `ok=true`, ID и положительный номер. Некорректный/пустой ответ оставляет черновик и вызывает ошибку, а не сообщение об успешной отправке. Отличаем «записан и ждёт кухню» от «принят». Проверяются отказ сервера, некорректный ответ, повтор с тем же ID и успешное восстановление. Если проверка статуса обнаружила реально сохранённую запись после потерянного HTTP-ответа, показ этой записи корректен.

Во время полного отсутствия связи новых заказов кухня получить не может: есть предупреждение. Не обещается восстановление доступа покупателя после удаления браузерного хранилища/анонимной сессии. Ранее сохранённый заказ остаётся у кухни.

## 3. Резервная копия и лимиты Free — пока нет подтверждённого рабочего механизма

Подготовлен `supabase/launch-audit.sql`: только READ ONLY, агрегаты размера/количества записей, RLS и наличия миграций/триггеров; без имён, телефонов, паролей, токенов. Владелец выполняет в SQL Editor той же базы. `pg_database_size` — техническая оценка, не доказательство расчёта квоты провайдера. Трафик/Realtime/backup/лимиты Auth нужно смотреть в кабинете.

По [документации Татнет](https://docs.tatnet.ru/docs/platform/supabase) Free имеет пределы места и трафика; при превышении запись и вход пользователей могут остановиться, после 7 дней без обращений возможна пауза. Предел именно этой базы (100 или прежние 500 МБ) уточнить в карточке. Не подключались платные опции.

**Операционный минимум:** в начале/конце смены смотреть карточку и предупреждения. Настроить доступные бесплатные уведомления провайдера; если их нет, это ручной контроль, а не автоматический мониторинг. Начальные пороги: предупредить при 70%, считать критическим 85% места/месячного трафика. При угрозе превышения — безопасно приостановить новые отправки до решения, не удалять данные наугад и не включать Pro автоматически. Измерить расход за несколько дней/неделю, особенно после накопления истории: резервная сверка каждые 3 секунды расходует трафик.

**Архив Git ≠ backup базы.** В доступных документах не подтверждены конкретная частота/глубина бесплатных копий и процедура восстановления этой базы. Публичный ключ не позволяет сделать полный консистентный backup Auth/ролей/данных. Не создаём ложную «резервную копию» из доступного публичного SELECT.

Перед запуском получить от Татнет существующий бесплатный способ резервирования: ежедневный снимок, плюс снимок до релиза; в РФ, с ограниченным доступом и шифрованием. Указать время последней успешной копии и целевые пределы потери данных/восстановления (предложение: до 24 часов и до 1 часа, **пока не гарантии**). Проверить наличие Auth UID/staff, функций/триггеров/RLS, заказов/отзывов/аудита и процедуру восстановления. Не восстанавливать поверх живой базы ради эксперимента. При запрете новых баз возможны проверка расшифровки/структуры локально и согласованная с провайдером безопасная проверка восстановимости; пока настоящая восстановимость не доказана, пункт остаётся открытым.

Не скачивать дамп с ПД в публичный GitHub/чат/iCloud по умолчанию. Не присылать секреты в чат. Автоочистку auth.users не включать: у заказов/отзывов есть связь с UID, удаление может повредить доступ/целостность. Сроки хранения и удаления требуют решения оператора.

## 4. Персональные данные и российское размещение

В подготовленной версии имя/телефон/адрес/состав/комментарий идут HTTPS-запросом непосредственно в существующий API Татнет, не в Google/Telegram и не через GitHub Actions. Статическая раздача сайта на GitHub Pages сохраняется; формы не добавляют ПД в URL. Библиотеки локальные, ключ в браузере только publishable, серверный секрет отсутствует. Закрытые таблицы и staff/RLS проверяются тестами; черновик с контактами временно хранится в браузере и удаляется после подтверждения сохранения. На общем планшете нужна защита устройства и выход staff.

Но домен `.tatnet.cloud` и работающий HTTPS не являются юридическим доказательством локализации. Нужно подтверждение провайдера о первичной записи в РФ, размещении PostgreSQL/Auth, логов/API-прокси/резервных копий, перечне привлечённых обработчиков и условиях поручения обработки. До такого подтверждения и заполнения фактических сведений в политике не заявляем полное соответствие требованиям РФ. Нельзя просто написать «всё в РФ» вместо проверки. Правовые страницы сохраняются, а часть текста о провайдере/сроках пока прямо содержит незавершённые сведения — это блокер, а не готовая юридическая редакция.

Оператор подтверждает реквизиты, основание обработки заказа, согласие на публикацию отзыва, сроки хранения и обязанности по уведомлениям/обращениям субъектов. Я подготовлю точечную редакцию после фактических ответов; выдумывать площадку/договор/сроки не буду.

## 5. Порядок запуска и быстрого отката

1. Получить ответы провайдера по Auth, backup и РФ; сверить цифры лимитов с потоком. При согласовании применить **005 только в существующей MissMaki-test** одним файлом; 001/002/003 не повторять. Если 004 уже применена для модерации, повторять её не требуется.
2. Выполнить read-only аудит, подтвердить успешный снимок и способ восстановления. Проверить пакет кандидата на том же тестовом приложении/существующей базе. Новых проектов нет. В production-кандидате нет тестовых диагностик: испытания выполняются отдельно в текущем тестовом приложении.
3. Зафиксировать один SHA кандидата и baseline, перечень тестовых №3/№4 и других тестовых записей. Исключить их из приготовления, не удалять историю автоматически. Пока тестовый сайт имеет публичные настройки той же базы, он может создавать заказы: перед допуском убрать доступ к его клиентскому checkout/диагностическим кнопкам или выдать там safe-fallback, оставив staff. Это не замена серверной защиты: прямой API всё равно проверяет права/лимиты.
4. Дождаться **отдельного явного разрешения владельца** на этот конкретный релиз. Только тогда объединять PR/готовить фактическую публикацию. Сейчас candidate не установлен в корень репозитория, исходная config выключена, DNS/CNAME рабочего сайта не менялись. Одного merge текущей ветки недостаточно для включения — подготовленный diff/артефакт ещё должен быть применён отдельным проверяемым релизом.
5. Публиковать один транспорт одновременно с отключением старых интеграций. Старые открытые вкладки могут сохранять прежний JS: закрыть старый GAS-приём на его стороне/через владельца интеграции и сверить уже отправленные заявки; удаления ссылки из нового HTML недостаточно, чтобы отозвать старый endpoint. Доступ к этим настройкам агенту не предоставлен, автоматически их не меняли. Контрольный заказ: запись → кухня → время → клиент, затем проверка отказа/отзыва. Не гонять один и тот же заказ сразу через два канала.
6. При ошибке включить **safe-fallback** из того же набора файлов через прежний способ публикации. Меню/цены/фото/корзина остаются; новые отправки закрыты, ранее записанные заказы продолжают обрабатываться. Это готовая обратная публикация, но время её применения зависит от GitHub Pages/CDN; мгновенный атомарный откат обещать нельзя. Позвонить/сверить сомнительные заказы до повторной отправки.
7. Не откатывать SQL/не удалять базу и новые заказы при откате HTML. Не делать git revert миграций на живой базе. `site-before.zip` хранить для восстановления прежнего оформления; его старый Telegram/GAS нельзя автоматически снова включать.
