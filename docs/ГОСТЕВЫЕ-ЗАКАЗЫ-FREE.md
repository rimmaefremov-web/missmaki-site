# Заказы без регистрации на существующем Татнет Free

Подготовлено 1 ноября 2026. **В MissMaki-test миграция 003 ещё не применена.** Auth, тариф, DNS и рабочий missmaki.ru не изменены. Новых заказов в настоящей базе на этом этапе не создавали. Предыдущие вымышленные №1/№2 сохранены.

## Что удалось проверить в настройках

Доступный публичный API по-прежнему возвращает `external.anonymous_users=false`. Ранее фактическая попытка гостевого входа вернула HTTP 422 `anonymous_provider_disabled`. [Документация Studio](https://docs.tatnet.ru/docs/platform/supabase-studio) описывает Email/URL/Rate Limits, но не подтверждает переключатель anonymous. Административного OAuth-подключения к кабинету нет; через публичный ключ параметры Auth менять нельзя. Поиск доступного плагина Татнет не дал результата. Это не доказательство, что оператор Татнет никогда не сможет включить режим; способ включения без его подтверждения не установлен.

Серверные параметры не менялись. Новая схема **вообще не зависит от регистрации или anonymous-входа Supabase Auth**.

## Подготовленное решение

Браузер создаёт криптографически случайный индивидуальный токен (256 бит) и хранит его локально только для этого проекта. В базе хранится его SHA-256, а не сам токен. Токен действует 30 дней; очистка браузера лишает покупателя доступа к своей сессии, но не удаляет заказ у кухни.

Перед созданием сессии, заказа или отзыва браузер решает небольшую вычислительную задачу в локальном Worker. PostgreSQL проверяет подпись, срок, решение и отсутствие повторного использования. Задача привязана к сессии, операции, номеру запроса и точному телу данных. Параметры защиты клиент менять не может. Никаких зарубежных CAPTCHA, ключей service_role в браузере, дополнительных серверов или платных Edge Functions нет.

Токен передаётся только в теле HTTPS RPC, не в URL. Серверные функции читают исключительно записи его владельца. **Таблицы orders/reviews/staff остаются закрытыми для прямых операций роли anon.** Вход администратора остаётся прежним: email/пароль + staff. Проверка цен, меню, доставки и слотов общая для обычного служебного и нового гостевого пути. Составы, фотографии и цены сайта не меняются.

Старая возможность отправлять заказы/отзывы через обычную самостоятельно созданную email-учётную запись закрывается для не-сотрудников: иначе ею можно было бы обходить новую защиту. Чтение старых собственных Auth-заказов и доступ сотрудников сохраняются. Никаких покупательских учётных записей Auth новая схема не создаёт.

## Серверные ограничения

Фиксированные окна; лимиты проверяет PostgreSQL, а не JavaScript:

| Операция | Начальные тестовые лимиты |
| --- | --- |
| Выдача вычислительных задач | 240 / минуту на проект |
| Новые гостевые сессии | 5 / минуту и 300 / сутки на проект |
| Создание заказов | 10 / минуту и 200 / сутки на проект; 5 / 10 минут на сессию |
| Отзывы | 5 / минуту и 100 / сутки на проект; 3 / час на сессию |
| Чтение статуса/своих отзывов | 120 / минуту на сессию |
| Свободные слоты | 120 / минуту на проект |

Ошибочная цена и другое отклонение бизнес-правил после правильной вычислительной проверки тоже расходуют бюджет и делают задачу использованной. Повтор уже сохранённого номера запроса возвращает прежнюю запись без дубликата. Проверка подписи — HMAC-SHA256; ключ создаётся в закрытой схеме БД, не нужен владельцу в чате или GitHub. Дополнительное расширение PostgreSQL не требуется.

Лимиты общие для проекта и отдельной сессии. **Мы не считаем подставляемый клиентом X-Forwarded-For доказанным IP.** Смена токена не обходит общий бюджет. Такая защита ограничивает спам и объём записей, но не гарантирует защиту от распределённой перегрузки: злоумышленник может израсходовать общий лимит и временно помешать другим клиентам. Нагрузочные испытания и инфраструктурная фильтрация остаются отдельной проверкой.

Публичная email-регистрация Auth сейчас включена на стороне провайдера. В новой схеме она не может использоваться для создания заказов/отзывов без защиты, но спам самих учётных записей Auth остаётся вопросом провайдера. После отдельного согласования можно запретить **новые регистрации**, сохранив вход уже созданных сотрудников. Мы не меняли `disable_signup` или Email provider и не предлагаем отключать весь email-вход.

## Что меняет 003_guest_checkout.sql

- Добавляет закрытую схему `missmaki_private`: секрет подписи, гостевые сессии, использованные задачи, счётчики.
- Добавляет guest_session_id в заказы и отзывы, сохраняя старые customer_id и данные. Ровно один тип владельца обязателен.
- Добавляет ограниченные public RPC для гостей; не выдаёт прямых прав на таблицы.
- Переносит общую проверку заказа во внутреннюю функцию; административные кнопки/версии/аудит не меняются.
- Сохраняет модерацию: approved публикуется, rejected не публикуется, автор rejected видит pending.
- Ничего не удаляет из существующих заказов/отзывов, не меняет Auth users, пароль администратора, тариф или настройки сервера.

Миграция — один SQL-файл, одна транзакция. При ошибке транзакция откатывается; не продолжайте отдельными кусками и не ослабляйте права. Успешную миграцию не запускайте повторно. Не делайте DROP/CASCADE для «отката» после появления гостевых заказов: сначала нужна отдельная проверенная процедура.

## Что проверено локально

- 31 автоматический тест: SQL, HMAC, сессии без Auth, цена, подмена подписи/тела, повтор задачи, повтор заказа, чужой токен, закрытые таблицы, обход через email, квоты, срок, старые данные и staff.
- 27 Chromium-проверок на размерах телефона, планшета и компьютера. Новый сценарий выполняет настоящий Worker и SQL-миграции в PGlite: корзина → гостевой заказ → все 8 времён → отказ → принятие и отклонение отзыва → reload. Количество Auth users не увеличивается.
- `npm run build:preview` создаёт отдельную статическую папку `dist-preview/`, не меняя исходный сайт.

Авторизация SDK в тестах моделируется, SQL и вычислительная проверка выполняются реально локально. **Это не результат на развёрнутом Татнет и не настоящий Safari.** Совместимость 003, ограничения тарифа/нагрузки, WebSocket, звук и физические устройства ещё нужно проверить в MissMaki-test. В гостевом режиме статусы сверяются раз в 3 секунды; клиент не получает прямого Realtime-доступа к закрытым таблицам. У кухни Realtime и резервная сверка сохраняются.

## Что нужно для проверки на настоящей базе

Сначала ознакомьтесь с готовым файлом `supabase/migrations/003_guest_checkout.sql`. Он подготовлен, но автоматически не исполнялся: публичный ключ не даёт таких прав. Переход на платный тариф не нужен.

1. Татнет → MissMaki-test → «Открыть Studio» → SQL Editor → New query.
2. Открыть готовый **003_guest_checkout.sql**, скопировать целиком → вставить → Run один раз. В файле ничего менять не нужно. **001/002 повторять не надо.** Если не хотите менять даже тестовую схему до дополнительного согласования, оставьте этот шаг невыполненным; код и проверки уже доступны для просмотра.
3. Опубликовать отдельную статическую тестовую копию по инструкции АДМИН-IPHONE-FREE.md. Не привязывать missmaki.ru и не менять его DNS.
4. Войти своим уже созданным тестовым администратором; пароль только в браузере. Открыть диагностику. При новой конфигурации она автоматически использует индивидуальные гостевые сессии без Auth, не вымышленные email-аккаунты.
5. Проверить весь процесс с iPhone/планшета; оценить задержку вычислительной проверки, восстановление сети, лимиты и модерацию. Тестовый заказ диагностики в конце отклоняется и остаётся в истории.

До выполнения этих шагов нельзя утверждать, что новый вариант работает на вашей базе. Рабочий сайт не переключается без вашего отдельного согласия.
