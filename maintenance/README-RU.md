# Служебная диагностика webhook MissMaki

Подготовлено 29.10.2026. Рабочий сайт, Google Apps Script и Telegram этим пакетом не изменены. Проверено локально с имитацией API; на рабочем боте не запускалось.

## Что уже установлено

mmCheckProductionWebhook сравнивает полный адрес вместе с ключом; отдельно адрес/ключ не показывает. mmConnectProductionWebhook останавливается при другом полном адресе и не умеет сохранять/возвращать прежний маршрут. Этих двух функций недостаточно. Не удаляйте их и не меняйте Код.gs/AvailabilityFix.gs ради диагностики.

## Самая короткая установка на iPhone

Один НОВЫЙ файл, одна вставка целиком. Замены старых файлов и «Выбрать всё» в редакторе не требуется.

1. На GitHub открыть maintenance/MMWebhookService.gs в ветке missmaki-update. Нажать кнопку копирования полного файла («Copy raw file»; при необходимости запросить настольный сайт Safari). Не копировать код по частям.
2. В рабочем проекте «Проект без названия»: «+» рядом с файлами → «Скрипт» → имя MMWebhookService. Вставить весь текст в начало НОВОГО файла, сохранить. Если редактор добавил пустую функцию myFunction, она может остаться внизу; в подтверждённом Код.gs такой функции нет. Не вставлять второй раз тот же файл.
3. Выбрать mmwsCheck → «Выполнить». Новое развёртывание НЕ нужно. Это ручная функция редактора, а не новый HTTP-обработчик. При необходимости разрешить запрошенные Google права своего проекта.

Только первый пункт копирует готовый файл; вручную править строки, URL или токены не нужно. В этой сессии нет подключённого Google-редактора/API, поэтому полностью без единственной вставки файла установить его я не могу. Если копирование GitHub не работает — остановиться и запросить полный файл одним сообщением; не заменять старые обработчики.

## Результат mmwsCheck

В журнал выводится JSON только с true/false. Его можно прислать целиком. Свойства проекта, backup и полный URL не присылать.

- ok / productionProject / productionBot — проверен ожидаемый проект и @MissMakiBot. На другом проекте или боте диагностическая операция останавливается; до чтения webhook тестового бота дело не дойдёт.
- sameDeploymentUrl — совпадает адрес /exec БЕЗ query-параметров.
- hookKeyConfigured — в Script Properties есть MM_CONFIRM_HOOK_KEY.
- hookKeyPresent — в текущем webhook есть единственный непустой mmHook.
- hookKeyMatches — mmHook совпадает со значением свойства.
- fullWebhookMatches — совпадает полный ожидаемый URL.
- webhookUsesTestDeployment — адрес совпал с известным тестовым /exec. В этом случае переключение блокируется; тестовый бот не изменяется.
- callbackUpdatesEnabled — Telegram разрешена доставка callback_query; пустой список allowed_updates означает стандартный набор Telegram, содержащий callbacks.
- pendingUpdatesEmpty — нет ожидающих обновлений на момент чтения.
- hasDeliveryErrorReported — Telegram сообщает прежнюю или текущую ошибку. Это НЕ доказательство текущей недоступности.
- backupExists / backupMatchesCurrent — есть ли закрытая резервная копия и совпадает ли с ней текущий маршрут/видимые параметры.
- previousHeaderSecretCannotBeRead — getWebhookInfo не возвращает прежний secret_token заголовка. Это ограничение API.

Диагностика не пишет свойства, не вызывает setWebhook/deleteWebhook, не посылает тестовый заказ и не проверяет URL POST-запросом.

## Контролируемое переключение — пока НЕ запускать

Все последующие функции — отдельные ручные действия, их не вызывает диагностика. Сначала показать результаты и получить отдельное подтверждение владельца.

1. mmwsPrepareSwitch: проверяет production проект/бота и сохраняет прежний URL и видимые параметры в закрытое Script Property MMWS_BACKUP_V1. Webhook и существующий ключ не меняются. Уже имеющаяся незавершённая копия не перезаписывается. Ранее завершённая копия архивируется в MMWS_HISTORY_*. Эти значения не публиковать.
2. Проверить условия прежней интеграции. Только если достоверно известно, что она НЕ использовала Telegram secret_token в HTTP-заголовке и НЕ имела вручную закреплённого IP, разрешено запустить mmwsConfirmPreviousStandardSettings. Нельзя подтверждать это предположением. Эти настройки не восстанавливаются достоверно из getWebhookInfo. При неизвестных настройках остановиться и изучить прежнюю интеграцию. Нестандартный хост, известный тестовый адрес и пользовательский сертификат блокируют подготовку.
3. После отдельного разрешения mmwsSwitchWebhook: сверяет сохранённую конфигурацию, личность бота и проекта, срок снимка (до суток), отсутствие ожидающих updates. При необходимости создаёт только MM_CONFIRM_HOOK_KEY. Проверяет текущий опубликованный обработчик служебным POST update_id:0 — он НЕ создаёт заказ и не посылает сообщение в Telegram. Лишь после этого вызывает setWebhook. Сохраняет список update types (добавляет callback_query при необходимости); стандартный пустой список сохраняется. drop_pending_updates всегда false. BOT_TOKEN/CHAT_ID не меняются, deployment не обновляется.
4. switchConfirmed:true означает подтверждённый адрес в getWebhookInfo, но ещё НЕ доказывает реальную доставку callback. Нажать кнопку в уже существующем помеченном тестовом заказе, проверить doPost, сохранение решения и изменение статуса на сайте. Повторно заказ для этого создавать не требуется. Если старый заказ старше срока хранения, сначала отдельно согласовать новый помеченный тест.

При switchConfirmed:false и webhookChangeMayHaveOccurred:true НЕ запускать переключение повторно вслепую: запрос мог быть принят Telegram до потери ответа. Сначала mmwsCheck, затем согласовать дальнейшее действие/откат. Копия и стадия сохраняются до изменения webhook.

## Откат — тоже только после разрешения

mmwsRollbackWebhook возвращает старый адрес, разрешённые обновления и max_connections из закрытой копии. При исходно отсутствовавшем webhook удаляет только новый webhook без удаления ожидающих updates. Если кто-то уже перенаправил webhook в третье место, функция остановится, не перезаписывая его. Ключ MM_CONFIRM_HOOK_KEY сохраняется, чтобы не ломать находящиеся в полёте запросы. Копия остаётся.

Откат маршрута НЕ отменяет уже принятые/отклонённые заказы и не воссоздаёт ранее доставленные updates. Исторический secret_token заголовка, загруженный сертификат и факт вручную закреплённого IP нельзя восстановить из стандартного ответа getWebhookInfo. Поэтому неподтверждённые нестандартные прежние настройки блокируют переключение, а не объявляются полностью резервируемыми.

Не запускать тестTelegram, не менять свойства BOT_TOKEN/CHAT_ID, не выполнять deleteWebhook вручную, не менять main, сайт, Код.gs, AvailabilityFix.gs или тестовый проект. Установка только служебного файла не требует обновления рабочего deployment: его версия продолжает использовать уже опубликованный doPost.
