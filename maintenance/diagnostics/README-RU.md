# Уточнение диагностики mmwsCheck — без замены обработчиков

Подготовлено 29.10.2026. В рабочем проекте ничего не установлено и не изменено.

## Почему старый результат не объясняет причину

В MMWebhookService.gs функция mmwsCheck вызывает mmwsContext_, затем читает сведения webhook и разбирает резервную запись. Все исключения перехватываются в одном catch, который печатает только {ok:false,noSettingsChanged:true}. Поэтому Apps Script показывает обычное завершение даже при отказе проверки.

Самая ранняя проверка mmwsContext_ объединяет сравнение ID скрипта и точного значения ScriptApp.getService().getUrl() с заранее заданным /exec. Несовпадение любого из них останавливает диагностику ещё до Telegram. URL сервиса может оказаться отсутствующим, другим развёртыванием или /dev; это отдельные сценарии для проверки, а не установленная причина вашего отказа. Затем могут отказать getMe/getWebhookInfo, проверка username/ID бота, чтение/разбор резервной записи. Последняя проверка mmCheckProductionWebhook проходила раньше, но это не заменяет актуальную поэтапную проверку.

По одному общему false точную причину установить невозможно. Это недостаток первоначальной диагностической функции, а не доказательство поломки заказов, неправильного токена или недоступности webhook.

## Исправление диагностики

Отдельный MMWebhookDiagnostics.gs с ручной функцией mmwdCheck. Она не меняет mmwsContext_, старые функции, Код.gs или AvailabilityFix.gs. Не создаёт HTTP-обработчиков, свойств, копий, триггеров, заказов или запросов к /exec. Из методов Telegram вызывает только getMe и getWebhookInfo. Ничего не переключает и не пишет. При несовпадающем ID проекта останавливается до Telegram; при другом username бота не читает его webhook. Все значения результата — true/false; URL, токены, body Telegram и тексты исключений не выводятся.

Сохранение резервной копии и переключение из старого служебного файла пока НЕ запускать. Проверки безопасности в нём остаются как есть.

## Одноразовая установка на iPhone

На GitHub открыть maintenance/diagnostics/MMWebhookDiagnostics.gs → Copy raw file (при необходимости настольный режим Safari). В рабочем Apps Script создать НОВЫЙ файл «+ → Скрипт» с именем MMWebhookDiagnostics, вставить весь текст один раз в начало и сохранить. Уже существующие файлы не выделять и не заменять. Пустая заготовка myFunction, если она появилась, может остаться; если такая функция уже осталась от прежнего добавления, дубли заготовки нужно устранить до запуска — нельзя создавать одинаковые имена функций. Сам диагностический файл не объявляет myFunction.

Затем выбрать mmwdCheck (НЕ mmwsCheck) → «Выполнить» и прислать полный JSON журнала. Развёртывание не обновлять. При неудобном копировании попросить полный файл в одном сообщении, без поиска или редактирования строк.

## Как читать булевы флаги

- scriptIdRead:false — не удалось прочитать ID текущего проекта.
- expectedScriptIdMatches:false — текущий ID не совпадает с предоставленным владельцем рабочим ID. Telegram не запрашивается; не удалять проверку.
- serviceUrlRead:false — чтение URL сервиса вызвало исключение. Другие доступные чтения продолжаются.
- serviceUrlPresent:false при serviceUrlRead:true — getUrl вернул пустое значение.
- serviceUrlMatchesExpected:false — значение getUrl отличается от зафиксированного production /exec. Отдельно serviceUrlUsesDev и serviceUrlUsesExec показывают тип адреса. Это НЕ означает, что отправка заказа или сам опубликованный URL не работают.
- propertiesReadable:false или botTokenConfigured:false — ошибка чтения свойств либо отсутствует BOT_TOKEN. Значение токена никому не передавать.
- getMeAttempted / TransportOk / HttpOk / JsonValid / ApiOk — этапы getMe. HttpUnauthorized и HttpForbidden показывают HTTP 401 и 403 без вывода ответа. TransportOk:false при Attempted:true означает исключение транспорта/UrlFetch, в том числе возможный отказ авторизации Google; само по себе не доказывает сетевой сбой.
- productionBotMatches:false при getMeApiOk:true — токен относится к другому username. Дальше обработка останавливается.
- botIdPresent:false — ответ getMe не содержит корректный числовой ID.
- webhookAttempted / TransportOk / HttpOk / HttpUnauthorized / HttpForbidden / JsonValid / ApiOk — такие же этапы чтения getWebhookInfo. Они не относятся к HTTP-ответу веб-приложения: эта функция /exec вообще не запрашивает.
- webhookInfoValid — корректная структура сведений Telegram. Далее sameDeploymentUrl, hookKeyPresent, hookKeyConfigured, hookKeyMatches раздельно описывают адрес и ключ.
- backupExists:true и backupJsonValid:false — имеющаяся резервная запись не разбирается как JSON. Она не удаляется и не выводится. backupStructureValid проверяет минимальную структуру копии.
- hasDeliveryErrorReported — Telegram хранит прежнюю/текущую ошибку; это не отдельная проверка нынешней доступности.
- ok:true — диагностическое чтение завершено, а не подтверждение исправного webhook. Отдельные флаги всё равно могут быть false. false также бывает нормальным значением: например backupExists:false до подготовки копии.
- unexpectedReadFailure:true — исключение на другом этапе, не текст ошибки и не раскрытие секрета.
- noSettingsChanged:true — функция только читала.

## Проверки

15 локальных сценариев, без живых Telegram-запросов: правильный проект, другой ID, другой URL, /dev, отсутствие URL, исключение чтения URL, отсутствие токена, 401/403 обоих методов, сетевое исключение, не-JSON ответ, тестовый username и неверная резервная запись. Подтверждены неизменность свойств, отсутствие методов изменения Telegram, вывод только boolean и отсутствие секретов. Общий отказ старой функции воспроизведён на фикстуре /dev; это пример, не установленная причина отказа у владельца.
